# 01 上电与安全 —— 明天照着做

> ⛔ **这一篇是操作手册，不是理论。第一天只看这篇。**
>
> 全程时间约 **2~3 小时**，不要赶。

---

## 零、先说人话：为什么第一天这么谨慎

你可能会想：不就是插上电跑个程序吗？

**力矩控制和位置控制是两回事。**

* **位置控制**：你说"去 30 度"，它慢慢走过去。指令错了，它慢慢走到错的地方。
* **力矩控制**：你说"出 5 牛米"，它**立刻开始加速**。指令错了，它**立刻加速到错的方向**。

⚠️ 而这台机器：

* **没有急停按钮**（客服确认）
* **没有抱闸**（断电直接掉）
* 三项电机保护**默认全关**（官方建议就这么用）

⇒ 出了事，**唯一能救的是 Ctrl+C**。所以第一天的每一步都要能随时停下。

---

## 一、开箱与固定（30 分钟）

### 1.1 ⛔ 底座必须固定牢

⚠️ 这不是"最好固定一下"，是**必须**。

原因：我们的辨识轨迹是**六个关节同时高频运动**，比一般演示动作激烈得多。

| 后果 | 说明 |
|---|---|
| 数据全废 | 辨识的前提是"基座不动"，底座一晃方程就不成立 |
| ⛔ 机器损坏 | 手臂甩起来带动整机，可能直接摔下桌子 |

⭐ **判据**：用手大力晃动手臂末端，底座**不能有任何可见位移**。

### 1.2 检查清单

- [ ] 底座固定牢（螺栓或重型夹具）
- [ ] 工作空间半径 **1 米内无人无物**（臂展 860 mm）
- [ ] ⭐ 手臂**下方垫软物**（毛巾/泡沫），高姿态测试时防掉落
- [ ] 电源、USB 线**不会被手臂扯到**
- [ ] 键盘在手边，**手指能立刻按到 Ctrl+C**

### 1.3 ⛔ 记住这两条

```
出事 → 按 Ctrl+C        （阻尼模式缓慢落下）
⛔    → 不要拔电源       （自由落体）
```

## 三、跑官方示例（40 分钟）

### ⭐ 为什么先跑官方的

**在碰我们的代码之前，先确认机器本身是好的。**

否则后面出错时，你分不清是"机器有问题"还是"我们代码有问题"——
第一天就会陷入这个泥潭。

### 顺序（一个一个来，每个确认正常再下一个）

```bash
cd <Panthera-HT_SDK>/panthera_python/scripts
```

| # | 命令 | 应该看到 |
|---|---|---|
| 1 | `python 0_robot_get_state.py` | 6 关节 + 夹爪都有读数；手推关节读数跟着变 |
| 2 | `python 1_Joint_PD_control.py` | 手臂走到 `[0, 0.7, 0.7, -0.1, 0, 0]` 并保持 |
| 3 | ⚠️ `python 2_gravity_compensation_control.py` | **第一次纯力矩**。不下垂、手推能拖动、松手停住 |
| 4 | `python 2_gravity_friction_compensation_control.py` | 比上一个**更容易推动** |

⚠️ 第 3 步是第一次跑力矩模式，**手放 Ctrl+C 上**。

⭐ 第 2 步的目标构型 `[0, 0.7, 0.7, -0.1, 0, 0]` 就是我们的 `Q_HOME`——
这不是巧合，我们是照官方抄的。

### ⚠️ 任何一步不正常

**停下来联系客服**，不要继续。这时候的问题是机器的，不是我们能解决的。

## 四、跑我们的 commission（60 分钟）

```bash
cd <panthera_project>
PYTHONPATH=. python scripts/commission.py
```

七步，每步之间会**停下来等你确认**。下面说每步在干什么、要看什么。

### 第 1 步　确认官方示例跑通

就是问你第三节做完没有。做完了按 `y`。

### 第 2 步　连接并读状态（**不发力矩**）

⭐ 这一步完全安全，只读不写。

**要看**：
* 6 个关节读数是否合理
* ⭐ **手动轻推每个关节，读数要跟着变**——尤其 J1 和 J6

⚠️ 如果某个关节推不动或读数不变，**停下来排查**。

### 第 3 步　⭐ 实测控制频率（仍不发力矩）

**这一步的数字决定后面所有增益。**

`官方`：客服说**没有实测值**（Q6 回答"未提供"），只给了单模组 3 kHz。
所以整臂到底多快，**只能我们自己测**。

**要看**：

| 读数 | 意义 |
|---|---|
| 平均 Hz | 官方阻抗示例注释是 200 Hz，达到就算正常 |
| **最大周期** | ⭐ 看门狗阈值按这个定（取 2 倍）|
| P99 | 抖动大不大 |

⚠️ 我们仿真里测过延迟敏感度，有个**陡峭的拐点**：
延迟 4 ms 时跟踪正常，**6 ms 时误差涨 15 倍**并出现力矩饱和。
所以这个数很关键。

📝 **记下来**：脚本会直接告诉你该把 `dt` 和 `watchdog_timeout` 设成多少。

### 第 4 步　⛔ 第一次发力矩

🔴 **手放 Ctrl+C 上。现在真的会动。**

**做法**：只给 J1 加力矩，从 0 缓慢升到 1.5 N·m，看它什么时候开始转。

⭐ **为什么选 J1**：它绕竖直轴转，**重力不参与**（见总索引 §二），
现象最干净——动了就是力矩推动的，没有别的解释。

⚠️ 其余关节零力矩，**会因重力下垂**——这是正常的。所以要垫软物。

**要看**：J1 在多大力矩下开始转 = **静摩擦力矩**。

📝 记下来：模型里 J1 的 `frictionloss` 是 `0.2`（`占位`值）。
实测值和它差多少，就是辨识要修正的量。

### 第 5 步　⭐ 验证限幅真的生效

**做法**：下发 10 倍超限的力矩，看实际反馈是不是被截断了。

⭐ **为什么要验**：我们一直假设"限幅会保护硬件"。
⚠️ **一个没被验证过的安全措施，等于没有。**

**要看**：实测峰值应该 ≈ 限幅值。如果明显超过，⛔ **立刻停止**，
在解决之前不要跑任何整臂力矩控制。

### 第 6 步　整臂重力补偿（第一次跑我们的完整链路）

链路：`控制器 → 安全层 → RealBackend → SDK → 电机`

**要看**：
* 手臂**不下垂**
* 手推能拖动，松手停住
* ⭐ **和官方第 3 个示例的手感应该一致**

⚠️ 如果手感差别很大，说明我们的模型或链路有问题——
但**别急着改代码**，先记下来，辨识之后大概率会改善。

### 第 7 步　标定碰撞检测阈值

⚠️ 这 10 秒**不要碰手臂**。

⭐ **为什么阈值要用数据定**：拍小了天天误报警，拍大了撞了也不停。
只能用"无外力时残差的实际波动"来定。

📝 记下来：脚本给出的 6σ 阈值。
⚠️ 它只对**当前工况**有效——高速运动时残差会更大，换工况要重标。

## 七、如果出问题

| 现象 | 先查 |
|---|---|
| 找不到 `/dev/ttyACM*` | USB 线、`dmesg \| tail`、串口权限 |
| 权限被拒 | `sudo usermod -aG dialout $USER` 然后**重新登录** |
| 读数全是 0 | 电机是否上电、SDK 配置文件路径 |
| 手臂突然软了 | ⚠️ 可能是指令被 SDK 静默丢弃，看 `backend.dropped` |
| 抖动/异响 | ⛔ **立刻 Ctrl+C**，不要"再试一次看看" |
| 频率远低于 200 Hz | 其他进程占 CPU？波特率设置？ |

⭐ **最后一条最重要：异常抖动或异响时立刻停。**
"再试一次看看"是很多事故的开始。
